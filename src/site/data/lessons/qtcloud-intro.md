# 量潮云简介

## 核心理念

量潮云的目标是成为帮助人类消除人机协作摩擦的第二大脑，核心是减轻认知负担。

平台的方法论是找到认知摩擦：从想法到落地之间的摩擦点。产品云回答从产品想法到落地的摩擦，基础设施云回答从基础设施想法到落地的摩擦——各云各回答一个领域内的摩擦，帮助人类把认知负担卸下来。

## 产品形态

量潮云的产品形态从 0.1 演化到 1.0，主线是各云从「互相认识」到「被派活」到「真干活」到「成行家」到「组团队」——一条从工具集合走向数字同事的路线。

起点是门户与协作目录。用户打开 cloud.quanttide.com，看到量潮云产品矩阵，协作目录里每个云自我介绍：我发布什么、我订阅什么。随着演化，用户不再记「哪个云干什么」，而是直接说要什么，系统把任务拆成步骤、标出每步由谁做；再往后，任务派下去，各云真的开始干活，用户从执行者变成验收者——这是 CoWork 模式与聊天工具的本质区别。终态是项目空间：复杂项目多个专家并行干活，成熟流程沉淀成团队资产，量潮云变成真正的数字同事团队。

协作目录是产品线的中枢，qtcloud Studio 是它的客户端载体。

## 当前现状

协作目录已具备事件目录、契约管理、流程编排三个核心页面，数据暂以本地配置演示。议事云与数据云两个子域已上线，协作目录尚未部署，cloud.quanttide.com 主域空白。

我们正以招聘政策案例为起点跑通端到端闭环：任务输入、拆解、多模块接力、交付草案、验收，逼出任务拆解、契约校验、验收机制三块能力。

## 我们的经营困难

量潮云的演化不是功能的累加，而是三个矛盾的逐步解决。

第一个矛盾是从「工具」到「同事」。系统第一次接管流程记忆，如果任务拆解不可靠，信任会在第一天崩塌，所以验收机制必须作为一等公民，而不是事后补丁。

第二个矛盾是从「设计」到「交付」。契约从注册表变成运行时验收标准，AI 输出从建议变成交付物，错误成本陡增。

第三个矛盾是从「专家」到「系统」。专家生态的前提是把「会做」变成「能教」，隐式经验显式化是长期的苦功夫，不是技术问题而是认知问题。

最大的风险是平台建设诱惑：在信任底座和真实业务缺失时先建平台，是最危险的顺序。

## 我们的应对思路

量潮云研发的核心方法是数据驱动的产品研发——用半结构化数据桥接文档与代码。

传统研发中，文档和代码是两条线，靠人来同步，人是最薄弱的环节。量潮云的做法是先把知识中可结构化的部分提炼为 JSON/YAML 契约，各端代码读契约不读 Markdown，形成知识增殖闭环：档案 → 契约 → 代码 → 新数据 → 档案。每轮循环，档案都变得更精炼，而非传统文档越写越乱。

这条链路已在管理后台落地：跨群搜索聊天记录、提取政策、抽取本体、按主题总结，招聘与课堂的政策都从这条链路沉淀。

## 平台化是方向

账号与支付是平台的地基。身份认证基于零信任假设，不刻意设置管理员角色，权限高了自然而然就是管理员；先做角色权限，复杂后再升级策略控制；用代金券机制加快支付验证。

客服云让系统在无人值守时正常运转：储电站模式、内外一体的工单系统。

研发系统的目的是解放人力用来创造，而绝非取代人力。「资本家系统」是设计启发——让老板和员工都干得更舒服，避免陷入零和博弈。

## 过往的成功经验

系统首先让产研团队内部用起来，最大程度验证系统是否有效。内部管理的重点在执行效率与工作质量：AI 增加了执行力度之后方向容易偏，而技术的工作最透明，相对来讲最好上系统。

最重要的经验是云从业务中长出来：先跑通闭环再横向复制，不被平台建设诱惑。0.1 的最小可用比想象中小，从做对的系统到做活的系统。
