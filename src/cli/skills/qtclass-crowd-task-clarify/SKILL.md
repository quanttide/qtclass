# qtclass-crowd-task-clarify

企业端丢来一句简单需求，本 skill 把它澄清、扩写成一份标准任务书草稿。

> **硬约束：缺关键信息先向需求方澄清，不得凭空编造交付物、平台与验收标准。**

## 任务书契约

### frontmatter（缺一不可）

```yaml
---
title: <名称>任务书
description: <一句话说清交付什么、在哪交付>
tags:
  requirement: fuzzy | semi | precise
  acceptance: closed | semi | open
---
```

- `title` 以「任务书」结尾
- `description` 一句话，能独立当卡片摘要用
- 两把尺是 Lite 实践页的筛选入口：取值只能是枚举三档，不得自造

### 正文结构

参照既有任务书（`apps/qtclass/src/lite/data/tasks/`，入库前扫一遍防重复）：

1. **H1** 与 `title` 一致
2. **项目背景与交付目标**：以谁的身份做、最终交付几样东西，交付物在此点名
3. **分交付物章节**：每个交付物一段，写清它要达成什么、底线是什么
4. **约束条件**：底线清单，越线即不通过
5. **验收标准**：逐条可判定

## 工作流

### 1. 澄清（缺什么问什么）

对照清单逐项检查，缺的直接追问需求方：

- 交付物是什么？几样？最终形态（发布 / 文档 / 数据 / 其它）
- 在哪交付？平台、渠道、账号主体
- 谁来验收？什么算通过？什么算不通过？
- 硬约束与禁项？（合规、变现方式、素材来源、资质）
- 时间与角色边界？（谁做、做到什么程度算完）

需求方答不上来的项，如实标注为待定，不代填。

### 2. 定两把尺

| 尺 | 取值 | 判法 |
|----|------|------|
| `requirement` 需求的精确程度 | `fuzzy` 模糊 | 只给方向，路径与交付形态自寻 |
| | `semi` 半精确 | 交付物与大方向给定，做法留白 |
| | `precise` 精确 | 交付物、平台、步骤级要求都明确 |
| `acceptance` 验收标准的开放程度 | `closed` 封闭 | 清单可逐条勾，机器或单人可判 |
| | `semi` 半开放 | 有清单，但留裁量空间 |
| | `open` 开放 | 以效果与人判为主（如「让陌生人想点」） |

标注是初判，交付时请需求方过目确认。

### 3. 扩写

- 背景写「以谁的姿态做完什么事」，不写教程与实现步骤——学员在做，不在看
- 每条验收标准回答三个问题：谁验、验什么、什么算过
- 约束只写底线，用「不得 / 严禁 / 任何…都不算通过」的句式
- 需求方原话里的关键词保留，不改成行话

### 4. 自检

- [ ] frontmatter 齐全，两把尺取值在枚举内
- [ ] H1 = title，title 以「任务书」结尾
- [ ] description 一句话说清交付
- [ ] 交付物在背景点名、在验收逐条对应，无悬空项
- [ ] 验收标准逐条可判定，无「做好一点」式软标准
- [ ] 与 `apps/qtclass/src/lite/data/tasks/` 既有任务书不重复

## 输出

草稿交需求方确认。入库按惯例归位：事实源 `data/profile`，展示层 `apps/qtclass/src/lite/data/tasks/`（两处字节一致），frontmatter 补两把尺 tags。
